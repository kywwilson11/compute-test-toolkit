# Research roadmap — gap analysis for advancing `computetest` to class-leading

**Source:** automated deep-research run on 2026-05-29 (112 subagents, 29 sources
fetched, 80 candidate claims extracted, 25 adversarially verified, 18 survived,
7 killed). Full raw transcript: `wf_5dc3bf89-af9` workflow run.

**One-line synthesis:** the gap between `computetest` and a class-leading
2025-2026 compute-MT toolkit isn't subsystem coverage — it's the absence of (1)
an **OCP ocp-diag-core**-shaped output/orchestration schema, (2) an
**instrument/fixture abstraction layer**, and (3) **measurement-system-quality**
scaffolding (gage R&R, station correlation, calibration tracking). These are
table stakes at hyperscaler MT organizations and named explicitly in OpenAI
Stargate and Google MTE job postings.

The single highest-leverage move: **refactor result emission to ocp-diag-core
JSON and wrap/match `pci_lmt`'s CLI contract.** That one change buys
hyperscaler-portable schema interoperability, a defensible per-lane data
contract, and a forcing function for the other gaps.

## Verified findings (survived 3-vote adversarial verification)

### 1. ocp-diag-core JSON output schema (confidence: high; vote: 3-0)

OCP maintains an official open-source diagnostic output spec
([github.com/opencomputeproject/ocp-diag-core](https://github.com/opencomputeproject/ocp-diag-core))
explicitly scoped to "Design Validation (HALT/HASS, Margin Testing) ...
Manufacturing Testing (L5/L6 board, L10 machine, L11 rack), Data Center Testing
(incoming QA, repair/maintenance), and Repair/reverse logistics (hardware RMA,
failure analysis)." Official SDKs exist as `ocp-diag-core-cpp` (Bazel, with
Python bindings) and `ocp-diag-core-python` (pure Python).

**Concrete addition:** `computetest/io/ocpdiag.py` that wraps existing result
objects into `TestRunArtifact` / `TestStepArtifact` / `measurementSeries`
elements, plus a CI job that validates emitted JSON against the published
schema. Add `--ocpdiag` flag to the CLI alongside the existing `--json`.

### 2. OCP `pci_lmt` CLI + per-lane schema (confidence: high; vote: 3-0)

OCP's PCIe Lane Margining Test
([github.com/opencomputeproject/ocp-diag-pci_lmt](https://github.com/opencomputeproject/ocp-diag-pci_lmt))
is the hyperscaler-blessed in-band margining tool (parallel Google fork; Oxide
maintains an alternative). Distributed as `ocptv-pci_lmt` on PyPI. Its CLI is
`pci_lmt [-h] [-o {json,csv}] [-e ERROR_COUNT_LIMIT=63] [-d DWELL_TIME=5]
[-a ANNOTATION] config_file`. Its per-lane schema is the column set a modern
PCIe MT tool must emit:

```
bdf, speed, width, lmt_capable, ind_error_sampler, sample_reporting_method,
ind_left_right_timing, ind_up_down_voltage, voltage_supported,
num_voltage_steps, num_timing_steps, max_timing_offset, max_voltage_offset,
sampling_rate_voltage, sampling_rate_timing, max_lanes, lane,
receiver_number, margin_type, step, sample_count, sample_count_bits,
error_count, ber
```

**Concrete addition:** `computetest/pcie/lmt_adapter.py` that either calls
`ocptv-pci_lmt` as a subprocess and ingests its JSON, or re-emits computetest's
own margining results in the same column set. Expose `--error-count-limit` and
`--dwell-time` flags with the same defaults (63, 5s) the OCP reference uses.

### 3. Astera Aries retimer-native diagnostics (confidence: high; vote: 3-0)

Astera Labs Aries Smart Cable Modules
([asteralabs.com/resources/faqs](https://www.asteralabs.com/resources/faqs/))
expose per-lane eye opening, equalization levels, junction temperature with
configurable alert thresholds, plus host-side and line-side loopback and PRBS
generation/checking. These are register-accessible (Astera COMET USB-I2C dongle
+ Python SDK; COSMOS SDK Nov 2025) and let an MT tool stress PCIe links
**without** an external BERT. Aries retimers power NVIDIA HGX H100 systems and
are expected on Blackwell.

**Caveat:** register map is NDA / SDK-gated, so the implementation depends on
Astera SDK access.

**Concrete addition:** `computetest/pcie/retimer/base.py` (vendor-agnostic
retimer interface: eye, EQ, Tj, loopback, PRBS BIST) + `aries.py` (SDK boundary
stub, populated when SDK access is granted). Record eye/EQ/Tj per lane in the
ocp-diag schema. Add a stress mode that drives PRBS in line-side loopback
during the BERT run.

### 4. PCIe 6.0 FEC-aware error reporting (confidence: high; vote: 3-0)

PCIe 6.0 uses 3-way interleaved RS-over-GF(2⁸) FEC: three consecutive bytes in
a lane belong to **three different ECC groups**, so a ≤16-bit burst hits at
most one byte per group. Post-FEC counts therefore *hide* the pre-FEC burst
structure that is the actual reliability signal. PAM-4 raw BER runs orders of
magnitude worse than the Gen5 NRZ 10⁻¹² target — FEC is mandatory at 64 GT/s;
the new compliance metric is **FBER ≈ 10⁻⁶**. Comparing a Gen6 pre-FEC count
to a Gen5 BERT verdict is a category error.

Sources: Synopsys "PCIe 6 Verification: FEC and CRC" blog (corroborated by
Cadence, Teledyne LeCroy, Tektronix, Keysight).

**Concrete addition:** extend the BERT engine's verdict logic to emit
`{pre_fec_symbol_errors, post_fec_flit_errors, fber_estimate,
burst_length_histogram}` as **distinct fields** alongside the existing
`correctable`/`uncorrectable`. Add an `--explain` mode that prints why a Gen6
pre-FEC count is not comparable to a Gen5 BERT number.

### 5. NVMe-MI 2.1 out-of-band path (confidence: high; vote: 2-1 ×2)

NVMe-MI 2.1 (ratified 2025-08-01,
[nvmexpress.org](https://nvmexpress.org/wp-content/uploads/NVM-Express-Management-Interface-Specification-Revision-2.1-2025.08.01-Ratified.pdf))
explicitly permits devices to implement **OOB-only**, **in-band-tunneling-only**,
or **both** — so `nvme-cli` (in-band) access is not guaranteed to surface
management state. Defines OOB Asynchronous Event Messages (health, temperature,
inventory, security state) with subscription, coalescing, and rate limiting,
traveling over MCTP to a BMC.

**Concrete addition:** `computetest/nvme/mi/` module using `libmctp` + an
Aardvark/I3C adapter (or QEMU-emulated BMC endpoint for the test path).
Implement AEM subscription and a Controller Health Status Poll cross-check
against the in-band SMART Log (LID 02h).

### 6. UNH-IOL NVMe-MI conformance as living checklist (confidence: high; vote: 3-0)

UNH-IOL publishes a formal NVMe-MI Conformance Test Suite — v23 (Jan 2025) was
verified during this research, superseded by v24 (Jul 2025) and **v25** (Feb
2026). 12 test groups including MCTP base/control/commands, NVMe error handling,
MI message processing, control primitives, management commands, admin command
set, management enhancement, VPD, and management endpoint reset tests. Each
test is marked `Mandatory` or `FYI`.

**Concrete addition:** `docs/nvme/unh_iol_v25_coverage_matrix.md` as a living
traceability table mapping each `Mandatory` test ID to a pytest node in
`tests/nvme/mi/`. CI gate that fails if any `Mandatory` test lacks a mapping.

### 7. OCP `nvme-cli internal-log` for telemetry (confidence: high; vote: 3-0)

The OCP nvme-cli plugin
([manpages.debian.org/nvme-ocp-internal-log](https://manpages.debian.org/testing/nvme-cli/nvme-ocp-internal-log.1.en.html))
retrieves and decodes **07h Telemetry Host-Initiated** and **C9h OCP Strings
Log** into human-readable text/JSON with `--telemetry-log` and `--string-log`
flags. Defined in OCP Datacenter NVMe SSD Spec v2.7.

**Concrete addition:** `computetest/nvme/ocp_telemetry.py` shells out to `nvme
ocp internal-log --output-format=json` and ingests the result into the ocp-diag
schema. Pytest fixture that captures a known-good telemetry snapshot per drive
family for regression.

### 8. Measurement-system-quality harness (confidence: high; vote: 2-1)

Named explicitly in OpenAI Stargate's Manufacturing Test Engineer posting:
"Knowledge of test station bring-up and validation methodologies (e.g., gage
R&R, correlation, calibration)." Corroborated by Google MTE posting requiring
"basic measurement system analysis (MSA) and Gage R&R studies." The toolkit
currently has zero operator/part/station ANOVA, zero station-to-station
correlation, zero calibration traceability.

**Caveat:** n=1-2 job postings; treat as "preferred by hyperscale," not
"industry-mandatory."

**Concrete addition:** `computetest/msa/` with `gage_rr.py` (crossed ANOVA on
operator × part × trial), `station_correlation.py` (Bland-Altman + Deming
regression across N stations measuring the same golden DUT), and a
`calibration_registry.yaml` with traceability dates and next-due intervals.

### 9. Instrument/fixture abstraction layer (HAL/MAL) (confidence: medium; vote: 2-1)

Hyperscale MT roles explicitly require integrating "custom electronics,
fixturing, and instrumentation" (OpenAI Stargate, verbatim). Industry-standard
practice (PXISA HAL/MAL, NI Semiconductor Test Library, Tektronix
`tm_devices` + PyVISA) decouples instrument-specific drivers from test
sequences. The toolkit currently uses only OS-level utilities (`nvme-cli`,
`ethtool`, `nvidia-smi`, EDAC, `lspci`) with no SCPI/VISA session management
beyond the existing `instruments.py` skeleton.

**Concrete addition:** extend `computetest/instruments/` with a base
`Instrument` class wrapping PyVISA sessions, subclasses for SMU/scope/external
BERT/switch matrix, and a `fixture_map.yaml` describing each station's
instrument inventory. **Test sequences reference instruments by role**
(`get_instrument("rx_eye_scope")`) **not by model.**

### 10. Diataxis documentation restructure (confidence: high; vote: 3-0 ×3)

Diataxis ([diataxis.fr](https://diataxis.fr/)) defines exactly four
documentation modes — tutorials, how-to guides, technical reference,
explanation — and explicitly addresses content/style/architecture. Pytest, the
most widely-adopted Python test framework, organizes its stable docs into
"Get Started," "How-to guides," "Reference guides," "Explanation" — matching
the quadrants. Independently adopted by Django, Cloudflare, NumPy.

**Concrete addition:** `docs/` restructured into `tutorials/`, `howto/`,
`reference/`, `explanation/`. Move existing content. Add new tutorial "Run
your first PCIe BERT in 10 minutes." Auto-generate reference from docstrings.
Tag each module's docstring with its quadrant entry.

## If you only do three things

Implement the **ocp-diag-core JSON emitter**, wrap **pci_lmt's per-lane schema**,
and ship the **MSA harness** with at least gage R&R and station-correlation
modules. The first two make the toolkit's output portable to any hyperscale
MT pipeline. The third proves you measure what you measure — which is what an
established team will ask before adopting anything new.
